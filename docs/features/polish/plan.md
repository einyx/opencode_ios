## Requirements Restatement

**The literal request:** make the OpenCode iOS Client feel "superpolished."

**What that actually requires.** All four dev-team personas independently converged on
the same first move: *"superpolished" currently has no definition of done."* A request
with no acceptance condition cannot be scheduled, cannot be reviewed, and cannot be
defended against regression. So the deliverable of this initiative is **not a bag of
styling tweaks** — it is a machine-checkable rubric plus an executable enforcement
layer, followed by a conformance-driven sweep of the codebase against the existing
"Quiet Tech" spec, followed by one carefully chosen vertical slice that establishes the
visual baseline.

### Premise corrections (measured, not assumed)

Three claims in the dev-team brief did not survive verification against the tree. They
change the backlog, so they are corrected here rather than averaged in:

1. **"87 TODO/placeholder markers in Views" → actually 0.** The 37 `placeholder` hits in
   the app are legitimate SwiftUI `TextField(placeholder:)` API usage and `L10n` key names;
   the remaining hits are fixture strings. **There is no TODO-cleanup phase to run.** The
   *seam* risk the personas identified is real, but it lives elsewhere: raw color
   literals, a second blue (`DesignColors.Semantic.info` at `QuestionCardView.swift:21` —
   a *different* blue from `Brand.primary`), a red error block that `docs/design.md`
   explicitly forbids (`MessageRowView.swift:648,651` uses
   `DesignColors.Semantic.error`), out-of-scale literal fonts, 57 hardcoded spacings, and
   5 `.font(.system(size: 1))` accessibility-probe hacks. **Phase 2 below is re-scoped to
   these seams** — it delivers exactly what the personas asked for ("fix or explicitly
   retire the broken seams before styling around them") without inventing work.
2. **The type-scale gap is bigger than "scattered literal `.system(size:)` calls."** The
   **token layer itself violates the mandated 22/16/13/12 scale**:
   `DesignTokens.swift:121` `display = .title3.weight(.bold)` = 20pt (spec: 22), `:127`
   `body = .body` = 17pt (spec: 16), `:133` `meta = .caption` = 12pt (spec: 13), `:136`
   `micro = .caption2` = 11pt (spec: 12), `:124` `headline = .headline` = 17pt — a
   *fifth* step not in the scale at all. So "migrate to tokens" alone is **not enough**;
   the token definitions must be rewritten too. This splits Phase 3 into a
   zero-visual-diff call-site migration (3a) and a single app-wide visual diff (3b).
3. **"Foundation pass with deliberately NO visual diff" is impossible as stated.** Because
   the tokens are non-conformant, *any* honest type-scale fix changes pixels on every
   screen. The Architect's real requirement — "later diffs stay reviewable" — is met
   differently, by making Phase 3b **the single, isolated, app-wide visual diff** (one
   commit, one screenshot-reviewable delta) rather than by pretending no diff exists.

### Constraints that shape the plan

- Design tokens over ad-hoc values; no raw system colors or literal font sizes in Views.
- No raw Swift errors in the UI.
- **Mandatory privacy review** for anything touching tokens, credentials, audio, or
  network transport.
- Tests isolated via per-test `UserDefaults` suite.
- Never disturb a live server (port 4096).
- No sibling app trees; upstream patches stay in `opencode-official/`.
- No credentials in tree or URLs.
- `xcodebuild build` and `xcodebuild test` run **sequentially**; use
  `./scripts/test_unit.sh` and `./scripts/test_ui.sh`.
- Per-feature docs under `docs/features/<name>/`; `docs/README.md` is the index;
  `docs/WORKING.md` is the decision log.
- **Screenshots must never be committed** (`docs/tests.md:216,224`). Baselines live in
  the gitignored `.occlient/` tree; the *rubric* records the expected description
  textually.

## Decision Points

These are surfaced, not resolved by averaging. Each blocks the phase that follows it.

### TENSION A — the gating fork: *conformance to Quiet Tech* vs. *richer than Quiet Tech*

**Settled in Phase 0, Step 0.1.** It determines what the rubric measures, therefore what
every later phase is.

| | **Branch A1 — Quiet Tech is the spec** | **Branch A2 — Quiet Tech v3 supersedes it** |
|---|---|---|
| **Rubric derives from** | `docs/design.md` as written; current violations are bugs | a new `docs/features/polish/design_v3.md` written *before* the rubric |
| **Type scale** | must literally be 22/16/13/12 → Phase 3b produces an **app-wide visual diff** | may be re-specified to match reality (`.title3/.body/.caption/.caption2`) → Phase 3b may be **zero-diff** |
| **Accent** | no new color; richness comes only from type, spacing, motion | may permit a second accent / richer surfaces — *this is PM's "feels richer but regresses the spec" risk, written down* |
| **Motion/haptics** | motion stays inside the existing motion table; haptics are additive and new | motion budget may be widened |
| **Backlog size** | large: token-layer rewrite + 102 call sites + 13 animation sites + 38 opacity + 57 spacing + haptics matrix | spec authoring (3–5 days) first, then the **same** implementation backlog, higher churn risk |
| **Cost** | ≈ 3–4 weeks | ≈ 3.5–4.5 weeks |
| **Failure mode** | the app stays restrained; PM's "less polished" worry is unaddressed | scope drift; the app stops looking like Quiet Tech; **Android-parity drift** widens |

**Default if undecided: A1.** Rationale: `docs/design.md` is a living top-level spec
already accepted as the project's visual direction; the "one accent, no gradients,
borderless-first" restraint is *load-bearing* for the product's identity, and the
brief's own evidence (5 ad-hoc colors left, 148 token uses, 265+ a11y calls) shows the
codebase is already ~85% conformant. A1 also converts the largest perceived-polish
lever (a real, consistent type scale) into a single reviewable delta instead of an
open-ended redesign.

**A3 (explicitly offered, may be rejected):** default to A1, but embed an **amendment
protocol** in the rubric — any deviation from `docs/design.md` requires (a) a numbered
clause ID in `design.md`, (b) a dated entry in `docs/WORKING.md`, (c) before/after
fixture screenshots. This gives an escape hatch that is *procedural* rather than
ad-hoc, which is what the PM/QA deadlock actually needs.

### TENSION B — what is the first PR

**Resolution: sequence, not exclusion.** PR #1 = **Phase 0 + Phase 1** (rubric +
failing-by-default lint harness). No pixels change, so no on-device acceptance is
re-triggered. It is simultaneously Dev/Architect's "foundation first," QA's "executable
tests first," and PM's precondition ("a checkable rubric before any code"). PM's pilot
screen is **not rejected — it is sequenced to Phase 5**, and defended in "First Vertical
Slice" below.

### TENSION C — how it is enforced

**Resolution: all three, layered, each with a distinct job.**

- **Static audit table** (`docs/features/polish/audit.md`) — read-only file/line evidence.
  **Explicitly labeled non-gating**; it is a snapshot, not a gate (Architect's need).
- **Ranked checklist** (`docs/features/polish/rubric.md`) — per-screen items with stable
  IDs and per-item predicates (PM + Dev's need).
- **Executable lint** (`scripts/polish_lint.sh` + `OpenCodeClientTests/DesignTokenTests.swift`)
  — the only thing that actually prevents regression (QA's need).

### Sub-tension D — strict scale vs. Dynamic Type (new, surfaced by the audit)

A literal 22/16/13/12 implemented as `.system(size:)` **does not scale with Dynamic
Type**; today's `.body`/`.caption`/`.title3` **do**. Naively enforcing the scale is an
accessibility regression in an app that already makes 274 accessibility API calls and
whose spec explicitly requires Dynamic Type support in the Host Profiles form
(`design.md:238`).

- **D1 (recommended):** define the scale with `Font.custom("SFProText-Regular", size: 16,
  relativeTo: .body)`-style custom fonts so the nominal size is exact *and* the type
  scales. **Requires a device spike** (Dynamic Type at `accessibility3` on a physical
  device) before it is adopted.
- **D2:** fixed sizes, no scaling, with an explicit accessibility waiver recorded in the
  rubric. Rejected — it trades a polish gain for an accessibility loss.
- **D3:** re-spec the scale to the semantic fonts (`.title3` / `.body` / `.caption` /
  `.caption2`) and amend `design.md`. This is only reachable under **Branch A2**. Under
  A1, D3 is rejected by definition.

**D1/D2/D3 must be decided in Phase 0 alongside TENSION A, because A1-vs-A2 determines
whether D3 is even on the table.**

### Phase 1 — Executable enforcement harness (PR #1: rubric + lint, no pixels)

**Files touched**

- NEW `scripts/polish_lint.sh` — bash 3.2 source scanner (repo convention), rules
  selected by flag (`--rules=type,color,spacing,opacity,motion,haptics,preview`), exit 0
  clean / 1 on violation, prints `file:line: rule: message`
- NEW `scripts/polish_lint_baseline.txt` — **ratcheting baseline** of known violations
  (the lint is green on day 1 but blocks *new* violations); shrinks monotonically
- NEW `OpenCodeClientTests/DesignTokenTests.swift` — swift-testing assertions on the token
  layer (`@testable import OpenCodeClient`, matching the repo's `import Testing`
  convention)
- MODIFY `scripts/test_unit.sh` — insert a `lint` phase **before** the build phase, using
  the existing `oc_phase` helper in `scripts/lib_test_observability.sh` (no new
  infrastructure)
- MODIFY `docs/tests.md` — document the new lint phase and its exit code

**Why a script and not an XCTest for the View layer:** the test bundle runs inside the
simulator sandbox and **cannot read the repository source tree**. So source scanning
must live outside XCTest. The XCTest half (`DesignTokenTests.swift`) asserts what *is*
reachable in-process — the token values themselves — which is where regressions are most
likely and most damaging.

**Steps**

1. Implement `scripts/polish_lint.sh` with a rule engine; each rule maps to one or more
   rubric IDs and is referenced by ID in its output so a failure is traceable to
   `docs/features/polish/rubric.md`.
2. Seed `scripts/polish_lint_baseline.txt` from the Phase 0 audit (every current
   violation, one per line, with its `file:line`).
3. Implement the negative test: the lint must *fail* on a deliberately offending fixture
   (e.g. a temp copy of a View with a raw color and an out-of-scale font).
4. Wire the lint into `scripts/test_unit.sh` as an `oc_phase lint` ahead of
   `oc_phase build`, so `./scripts/test_unit.sh` fails fast and the failure is recorded in
   the run's `events.tsv` / `state.tsv` (existing observability contract — no new format).
5. Add `DesignTokenTests.swift` asserting: `Brand.primary` == `#3B82F6`, `Brand.gold` ==
   `#D9A621`, `DesignCorners` == {small 6, medium 12, large 16},
   `DesignSpacing.cardPadding` == the value the spec's clause dictates, and — under
   Branch A1 — the four type sizes are exactly {22, 16, 13, 12}. These assertions are the
   executable form of the rubric's token half.
6. Add `DesignAnimation` budget assertions (no preset may exceed the spec's 0.35s
   response / 300ms duration ceiling).

## First Vertical Slice — recommendation and defense

**Recommendation: the chat message stream** (`MessageRowView`, `ToolPartView`,
`FileCardView`, `PermissionCardView`, `QuestionCardView`, `TodoListInlineView`,
`TaskNotificationCardView`, `PatchPartView`) — **explicitly excluding the composer, the
voice rail, and `ChatTabView+VoiceInput.swift`.**

**Defended against the alternatives:**

**vs. Host Profiles** (PM's "smaller surface, faster baseline"):

1. **It collides with the live work.** The working tree already carries an uncommitted
   host-profile change (`Models/HostProfile.swift` removing
   `HostProfileError.cannotDeleteOnlyHost`, `Support/L10n.swift` removing
   `hostDeleteOnlyHostError`, `AppState+HostProfiles.swift` +70 lines, plus
   `ConnectionTests`/`HostLifecycleTests`/`TestDoubles`). A pilot slice on the same
   surface guarantees a merge conflict in the highest-churn file in the repo and
   re-triggers acceptance on the PR that is already waiting.
2. **It has the least polish headroom.** `HostProfilesView` is a native `Form` — it
   already *looks* native, which is exactly what "polish" does not improve. The perceived
   gain from styling a Form is near zero.
3. **It does not define the grammar.** The chat message stream is where the type scale,
   the three card shapes, the single-accent rule, the motion table, and the error-surface
   rule are all load-bearing. Everything in Phase 7 inherits those decisions. A pilot
   that does not exercise them teaches the team nothing about the rest of the app.

**vs. Settings** (the "smallest possible pilot" instinct):

1. Settings is the best *second* slice — it tests whether the grammar generalizes to a
   grouped `Form` (the accent-in-a-picker rule at `SettingsTabView.swift:122`) — but it
   is a poor *first* slice because a Form's polish is dominated by system chrome, not by
   our decisions.
2. It also carries a specific spec obligation (`design.md:238`: Dynamic Type on
   `LabeledContent`) that is worth doing *after* the scale is settled, not before.

**vs. "the whole chat screen"**: the composer contains the stop/send stacked relationship
(`design.md:109-110`), the voice rail, and the mic capsule — all of which PRs #215/#216
are awaiting on-device acceptance for. Any whitespace or motion change in that region
re-opens the acceptance loop. Excluding it is what makes this slice safe to land while
those PRs are pending.

**Why the chat message stream is the right first slice:**

- It is where the product lives: `design.md:218` "The Chat view occupies 90% of the
  user's interaction time."
- It is **render-only** — no network, no audio, no credentials, no host state → the
  privacy-review surface is limited to what is rendered, and it cannot disturb the live
  server on 4096.
- It is **already test-covered**: `ToolCardsUITests.swift`,
  `TaskNotificationUITests.swift`, `SessionIndicatorUITests.swift` exist, and
  `docs/tests.md:240` already documents the `oc_toolcards` / `oc_toolcards_collapsed`
  screenshot QA for exactly these tiles.
- It is **fixture-renderable** — `Views/Support/UITestFixtures.swift` + the deterministic
  screenshot harness (`docs/tests.md:185-216`) produce reviewable screenshots **without a
  live server**.
- It carries the **highest-density set of confirmed spec violations** (stripe width,
  corner radius, error color, missing entrances, `DisclosureGroup` vs. custom spring, hit
  targets) — so it converts the rubric from theory into visible, reviewable proof.

**And it must come *after* Phases 1–3, not before** — PM's own argument ("polish layered
on broken seams reads as broken") applies to the type scale exactly as much as to a TODO:
a pilot built on `.body` = 17pt and `Display` = 20pt is a pilot on a broken base, and its
screenshot review would approve pixels that Phase 3b then invalidates app-wide. This is
why TENSION B resolves to *sequencing*, not to "pilot first".

## Risks

### HIGH

- **H1 — TENSION A is left undecided.** Every downstream phase measures something
  different depending on the branch; a mid-course flip wastes Phase 2–3 and forces a
  second app-wide visual diff. *Mitigation:* Phase 0 Step 2 is a hard gate with a default
  of **A1**; the rubric's ID scheme and the lint rules are written to be branch-neutral
  where possible so only Phase 3b is branch-dependent.
- **H2 — Type-scale conformance is an accessibility regression.** Implementing
  22/16/13/12 with `.system(size:)` freezes Dynamic Type scaling on an app that makes
  274 accessibility API calls and whose spec mandates Dynamic Type in Host Profiles.
  *Mitigation:* D1 (`Font.custom(..., relativeTo:)`) with a **physical-device Dynamic Type
  spike before adoption**; D2 requires an explicit, recorded accessibility waiver; D3 is
  only available under Branch A2. The spike is a Phase 3b entry condition, not a
  follow-up.
- **H3 — Polish diffs collide with PRs awaiting on-device acceptance.** The working tree
  already carries an uncommitted host-profile change; PRs #215/#216 are unmerged pending
  device testing. Any whitespace/motion change in `ChatTabView.swift`,
  `HostProfilesView.swift`, or `Support/L10n.swift` re-opens an acceptance loop the team
  is already waiting on. *Mitigation:* explicit file exclusion lists per phase (Phase 2
  excludes `HostProfilesView`; Phase 4 excludes `voiceRail*` and
  `ChatTabView+VoiceInput.swift`; Phase 7 orders the composer last); every phase names
  its collision set in the PR description; the initiative lands on a branch off `master`
  only after the host-profile diff is committed.
- **H4 — The lint becomes a ritual, not a gate.** A lint with 40+ rules that fires on the
  team's own work gets disabled or allowlisted into meaninglessness. *Mitigation:* the
  **ratcheting baseline** (new violations fail; existing ones are listed and must
  shrink); every rule prints the rubric ID it enforces; the baseline's line count is a
  tracked, monotonically-decreasing metric reported at each phase exit.

### MEDIUM

- **M1 — `scripts/test_unit.sh` gains a phase and starts failing for unrelated reasons.**
  A lint failure would be indistinguishable from a test failure to someone reading only
  the exit code. *Mitigation:* the lint runs as a named `oc_phase lint` and is recorded
  in `events.tsv`/`state.tsv` under the existing observability contract; the failure
  message names the script and the rule IDs; the existing exit codes (0/65/73/74) keep
  their meanings.
- **M2 — `ChatTabView.swift` is 2,279 lines and `MessageRowView.swift` is 1,015.** Edits
  of this size are unreviewable, which is the opposite of what the initiative promises.
  *Mitigation:* Phase 5 is split into ≥5 separate PRs, each one concern (geometry, color,
  entrance motion, tool-card disclosure, hit targets), each independently
  screenshot-reviewed; no PR mixes a conformance fix with a refactor.
- **M3 — The rubric measures the wrong thing.** A rubric written from the spec alone may
  measure conformance that no user perceives. *Mitigation:* the rubric carries both a
  *conformance* family and a *felt-quality* family (motion rhythm, response latency of
  the composer, empty-state tone, error-message tone); Phase 0 Step 5 ranks by
  user-visible impact ÷ review cost so the felt-quality items get real budget.
- **M4 — Screenshot baselines cannot be committed.** `docs/tests.md:216,224` forbids
  committing screenshots, so there is no in-repo regression baseline for pixel changes.
  *Mitigation:* baselines live in gitignored `.occlient/`; the rubric stores the
  **textual description** of each expected rendering (the same "read the image and
  confirm" protocol `docs/tests.md:216` already uses); the lint + token XCTest carry the
  machine-checkable half.
- **M5 — The watch target is left permanently non-conformant.**
  `WatchAmbientApp.swift` uses `.font(.system(size: 42))` and `.foregroundStyle(.orange)`
  with zero token usage. *Mitigation:* explicitly marked `DEFERRED` in the rubric with a
  reason (Experimental target, no acceptance loop value), not silently omitted.

### LOW

- **L1 — New L10n keys.** The rubric may require new localized strings (e.g.
  haptic-related hints). `Support/L10n.swift` has 512 keys across en/zh-Hans and is
  currently **modified** in the working tree → merge friction. *Mitigation:* add all L10n
  keys in a single phase-scoped commit; never edit `L10n.swift` while the host-profile
  diff is uncommitted.
- **L2 — `DesignTokens.swift` grows.** The type, motion, and haptic tokens may push it
  past ~350 lines. *Mitigation:* split into `DesignTokens.swift` (color/type/spacing/corner)
  + `DesignMotion.swift` + `DesignHaptics.swift`, keeping the existing public names so
  the 148 `DesignColors.*` call sites do not change.
- **L3 — Localized layout breakage.** `SessionListView.swift:29` uses a fixed
  `width: 88` for the close button; the scale and spacing changes can overflow in long
  locales. *Mitigation:* Dynamic Type + `zh-Hans` + long-locale checks are named in the
  rubric's per-screen acceptance list and are a Phase 5 exit item.
- **L4 — `grep` portability.** The lint uses `grep -E` / `grep -r`; macOS BSD grep
  differs from GNU grep. *Mitigation:* the lint is bash 3.2 + BSD-compatible (matching
  `scripts/lib_simulator.sh` and `scripts/lib_test_observability.sh`); it is written
  against the same conventions, not GNU-only flags.

**Value inflection points**

- **End of Phase 1 (≈1 week):** the app gains a regression guard. Every later phase
  becomes cheaper to review.
- **End of Phase 3b (≈3 weeks):** the app gains a *correct* type scale — the single
  highest-leverage visible improvement, delivered as exactly one reviewable diff.
- **End of Phase 5 (≈4.5 weeks):** the app gains the polished chat stream — the surface
  where the user spends 90% of their time — and the first sensory layer (motion +
  haptics) that is currently absent entirely.

**Cost of doing nothing:** haptics stay at 0, motion stays at 13 sites against a 4-entry
spec motion table, 1 preview covers 16+ screens, and the type scale stays 5 steps wide
with a 2pt spread on the primary reading surface.

## Open Questions for the Team

1. **The `OpenCode` reply title — spec or code?** `design.md` §QT-SPEAKER requires an
   `OpenCode` text title on every AI reply, but `MessageRowView.swift:687` deliberately
   omits it (`// No "OpenCode" speaker title — the user's blue left-bar vs the`). One of
   them is wrong. The reply title is a visible change to the surface the user spends
   90% of their time in, so it needs a decision, not a bug fix. Two options:
   **(a)** the code is right and §QT-SPEAKER is superseded — amend the spec and re-point
   `POL-TYPE-11` at the *current* behaviour (user bar vs. container-free reply);
   **(b)** the spec is right and the title is added — `POL-TYPE-11` stays a FAIL and the
   work lands in Phase 5. This was found during the Phase 0 audit, not during planning.
   **Until it is answered, `POL-TYPE-11` cannot be actioned and PRY-28's scope is
   ambiguous.**
2. **The user-message bubble radius is not settled by the spec.** §QT-CARD assigns 12 pt
   to information/action cards and 16 pt to sheets, and the user message with its
   `accent.muted` fill is described in §QT-MESSAGE — which specifies the stripe and the
   fill but **no radius**. The token file's own doc comment says `DesignCorners.large`
   is "message bubbles, sheets" (`Utils/DesignTokens.swift:214`). The current code uses
   `large` at `MessageRowView.swift:636`. The plan's P5-1 assumed 12 pt; the spec does
   not actually say so. **Decide the radius and record it as a clause**, otherwise
   PRY-28 changes a value the spec never defined.
3. **Who owns the rubric after Phase 0?** A rubric with no owner decays into a document
   nobody enforces. The lint in Phase 1 is what actually prevents regressions, and its
   baseline only shrinks if someone keeps ratcheting it.
4. **Is the watch companion in scope for "superpolished"?** Currently deferred (v1
   excludes `OpenCodeWatch/WatchAmbientApp.swift`, which has zero token usage and uses
   raw `.font(.caption)`, `.font(.system(size: 42))`, `.foregroundStyle(.orange)`). It
   gets a visible `DEFERRED` rubric row, not silent coverage. If it should be in scope,
   add a Phase 7.5 with its own token subset.
5. **If you believe there are 87 real seams that were not found, say where.** The
   measured count of TODO/FIXME markers in the target is **0**; the seam inventory in
   Phase 2 is the 102 real violations the audit found. If there is a set of seams the
   audit missed, name them and Phase 2 is re-audited before it starts.
