# OpenCode Web API Technical Documentation

> Last verified: 2026-08-23 · origin/dev @ 03bba464d

> This document is compiled from the official OpenCode documentation (opencode.ai/docs) and the source code of the anomalyco/opencode repository, with the goal of systematically describing OpenCode's web interface and HTTP API capabilities.

## 1. Overview

OpenCode is an open-source AI coding agent that uses a **client/server architecture**. Starting `opencode` brings up the TUI and the HTTP server together, with the TUI acting as the front-end client talking to the server. This decoupled architecture brings the following advantages:

- The web interface, desktop app, and IDE plugins can all connect to the same backend as **different clients**
- Support for **programmatic invocation** through the HTTP API

### 1.1 Repositories and Version Notes

| Repository | Description |
|------|------|
| **anomalyco/opencode** | The official main repository, providing `opencode serve`, `opencode web`, and the complete HTTP API |
| **opencode-ai/opencode** | A community fork, already archived; the project has migrated to Crush |
| **chris-tse/opencode-web** | A third-party web UI: a React front end built on the OpenCode API |

The clone in this repo is `anomalyco/opencode` (the official main repository), which includes the serve/web commands and complete HTTP API support.

The current API system is divided into two layers:

- **Legacy API** (no `/api` prefix): instance-level routes that locate a specific workspace through the `x-opencode-directory` request header or a query parameter.
- **V2 API** (`/api` prefix): the newer endpoints defined by the Protocol layer, designed specifically for the various SDKs and cross-workspace clients.

## 2. Startup Modes

### 2.1 Headless Server (API only)

```bash
opencode serve [--port <number>] [--hostname <string>] [--cors <origin>]
```

| Argument | Description | Default |
|------|------|--------|
| `--port` | Listening port | `0` (automatic: tries 4096 first, and takes a random free port if that one is occupied) |
| `--hostname` | Listening address | `127.0.0.1` |
| `--mdns` | Enable mDNS discovery (binds `0.0.0.0` automatically) | `false` |
| `--mdns-domain` | mDNS domain | `opencode.local` |
| `--cors` | Allowed CORS origins (may be passed multiple times) | `[]` |

> If no port is specified explicitly, the server tries to bind port 4096 first; if that port is already taken, it automatically falls back and assigns a random available free port (the `startWithPortFallback` mechanism). Developers can specify the port explicitly through the `--port` command-line argument or the `server.port` setting in the configuration file, with the command-line `--port` taking the highest precedence; the `server.port` setting is optional and has no value by default.

### 2.2 Web Interface (API + built-in web UI)

```bash
opencode web
```

- Listens on `127.0.0.1` by default; the port policy is the same — try 4096 first and fall back to a random free port on conflict
- Once the service is ready it automatically launches the system default browser to open the web page
- Under the hood it reuses exactly the same HTTP API service as `opencode serve`

### 2.3 Authentication (optional)

```bash
OPENCODE_SERVER_PASSWORD=your-password opencode serve
# or
OPENCODE_SERVER_USERNAME=admin OPENCODE_SERVER_PASSWORD=secret opencode web
```

- The default authentication username is `opencode`
- Authentication settings apply to both `opencode serve` and `opencode web`
- If no password is configured, the server prints a warning at startup and exposes the service without authentication

## 3. OpenAPI Specification

- **URL**: `http://<hostname>:<port>/doc`
- **Example**: `http://localhost:4096/doc`
- **Format**: OpenAPI 3.1
- **Purpose**: inspect request/response types, generate SDKs, preview via Swagger
- The endpoint response format is JSON (dynamically generated by `OpenApi.fromApi(PublicApi)`) and includes a compatibility layer for legacy routes

## 5. Typical Usage Scenarios

### 5.1 Sending a Message Programmatically

```bash
# Create a session
curl -X POST http://localhost:4096/session -H "Content-Type: application/json" -d '{"title":"My Task"}'

# Send a message (replace :sessionId)
curl -X POST http://localhost:4096/session/:sessionId/message \
  -H "Content-Type: application/json" \
  -d '{"parts":[{"type":"text","text":"Explain what this code does"}]}'
```

### 5.2 Sending Asynchronously (without waiting for the AI to finish)

```bash
curl -X POST http://localhost:4096/session/:sessionId/prompt_async \
  -H "Content-Type: application/json" \
  -d '{"parts":[{"type":"text","text":"Refactor this function"}]}'
```

### 5.3 File Search and Reading

```bash
# Find files
curl "http://localhost:4096/find/file?query=config"

# Read a file
curl "http://localhost:4096/file/content?path=src/main.go"
```

### 5.4 Driving the TUI from an IDE Plugin

After specifying the address of the server the target TUI is bound to via the `--hostname` and `--port` arguments, an IDE plugin can call endpoints such as `/tui/append-prompt` and `/tui/submit-prompt` on demand, to pre-fill and submit prompt content automatically.

### 5.5 Using the V2 API (SDK clients)

```bash
# List sessions
curl "http://localhost:4096/api/session?limit=10&order=desc"

# Send a prompt (V2 uses prompt.text, not the legacy parts shape)
curl -X POST http://localhost:4096/api/session/:sessionID/prompt \
  -H "Content-Type: application/json" \
  -d '{"prompt": {"text": "Hello"}}'
```

## 7. Comparison with OpenClaw (brief)

| Dimension | OpenCode | OpenClaw |
|------|----------|----------|
| Entry point | TUI / Web / IDE / CLI | Messaging platforms (WhatsApp/Telegram etc.) |
| Positioning | A coding agent | A lifestyle / automation gateway |
| API | Complete HTTP API + OpenAPI + V2 Protocol | Gateway-first, not a general-purpose HTTP API |
| Memory | Sessions + AGENTS.md + workspace sync | MEMORY.md / SOUL.md etc. |
| Extensibility | MCP / Skills / Worktree / Workspace | Skills (ClawHub) |

The Web + API two-layer architecture adopted by OpenCode provides a mature and reference-worthy engineering implementation pattern for building agent systems that balance a "unified interaction entry point" with "flexible programmatic invocation".
